# 화·수 기능 점검에서 보완한 결정

2026-11-24, 3번 브랜치. 사용자 요청의 지원·지원자 관리·알림 기능을 팀 SQL에 맞춰 점검했다.

- **기존 0300/0301은 수정하지 않고 0302로 보완:** 이미 실행했을 수 있는 팀 DB에 테이블 재생성을 요구하지 않기 위해 새 마이그레이션에서 함수를 교체하고 정책을 보완한다.
- **가입 직후 role=null은 지원 불가:** 실제 0100은 역할 선택 전 null을 허용한다. SQL의 `<>`만으로는 null이 차단되지 않으므로 `IS DISTINCT FROM`으로 비교한다.
- **탈퇴 회원의 접근과 지원자 선정 차단:** 실제 profiles의 deleted_at을 확인하고, 수락할 대상도 활동 중인 프리랜서인지 확인한다. 자신의 탈퇴 여부를 bool로 반환하는 RPC만 추가하며 profiles의 공개 컬럼 권한은 바꾸지 않는다.
- **목록을 30개씩 조회:** Supabase의 응답 행 수 제한으로 오래된 지원/거절 이유가 조회 목록에서 영영 빠지는 것을 막는다. 전체 건수와 다음/이전 페이지를 제공한다.
- **지원자 이름은 허용된 name만 조회:** 실제 profiles는 이메일 SELECT 권한을 공개하지 않는다. 지원서 목록에 관계 조회를 사용하되 name만 선택하고 공개되지 않은 프로필은 순번으로 표시한다.
- **알림 읽음 후 layout 재검증:** 페이지의 숫자만 바뀌고 공유 헤더의 숫자는 남는 문제를 방지한다. 종 컴포넌트의 서버 개수 변경 시 클라이언트 상태도 새로 시작한다.
- **인증 초기화 전에 connection 대기:** Supabase Auth의 시간 의존 초기 작업이 Next.js 사전 렌더링에 섞이지 않도록 담당 서버 진입부와 종 컴포넌트에서 실제 요청을 기다린다. 사용자별 인증 결과를 캐시에 저장하지 않으며 공통 Supabase 파일도 수정하지 않는다.
- **로컬 브라우저용 인증/API 대역:** 공용 Supabase 키 없이도 실제 Next.js 화면과 Server Action, SQL/RLS를 연결해 확인하기 위해 사용했다. 테스트 파일은 app route가 아니고 127.0.0.1에만 바인딩한다. 실제 인증/권한 서버 대체물로 배포하지 않는다. 실 Supabase·PostgREST·Realtime 검증과 구분한다.

다른 담당 폴더, 공통 헤더·인증 화면, profiles/projects SQL과 package.json/lock은 수정하지 않았다. 4번의 계약 생성은 저장된 `accepted_agreed_amount`와 `application_id`를 인계하는 기존 약속을 유지한다. 실제 헤더 삽입·계약 생성 연결은 각 담당자가 수행해야 한다.
