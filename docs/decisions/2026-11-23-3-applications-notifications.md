# 지원·알림 초기 결정 기록

2026-11-23, 3번. RFP 원문은 저장소에 없으므로 제공된 사용자 요구·TEAM.md에 명시되지 않은 구현 선택을 기록한다. 다른 담당자의 합의가 필요한 연결점은 확정된 팀 합의로 간주하지 않는다.

| 선택 | 이유 | 상태 |
| --- | --- | --- |
| DB RPC로 업무 변경과 알림을 원자적으로 처리 | 여러 Supabase 요청은 Server Action 하나에 있어도 DB 트랜잭션이 아님 | 구현 |
| 프로젝트 행을 먼저 잠그고 그 뒤 지원서 변경 | 지원·선정·마감이 겹칠 때 이중 선정과 미처리 지원 방지 | 구현, 실제 동시 세션 부하 검증은 남음 |
| applications에 accepted_agreed_amount/accepted_at 추가 | 4번 테이블을 수정하지 않고 협의 시작 금액을 전달 | 제안 인터페이스, 4번 확인 필요 |
| 협의 시작 금액은 1원 이상 원 단위 정수 | 소수 금액·무의미한 음수·0 차단. 최종 합의는 4번 화면에서 별도 처리 | 구현 |
| 자기소개 최대 5,000자, 기간 최대 3,650일 | 과도한 입력을 막고 UI·서버·DB 검증 통일 | 구현 |
| 프로필 name/bio/category/skills를 초기 완성 조건으로 사용 | 최소한의 소개와 기술 정보가 있는 지원을 받기 위해 | 1번과 통일 필요 |
| 직접 모집 마감은 recruiting에서만 허용 | 예정·계약 중 상태의 무분별한 변경 방지 | 2번 확인 필요 |
| 마감 시각 경과 후에도 마감 RPC 처리 전 선정 허용 | 이미 받은 지원을 검토할 여지를 유지. 실제 closed 처리 후는 선정 금지 | 2번 확인 필요 |
| 이미 직접 거절된 지원자에게도 모집 마감 알림 | 사용자 요구의 '지원자 전원'을 따르며 기존 거절 이유는 유지 | 구현 |
| 영구 중복 지원 금지, 거절 기록 유지 | TEAM.md의 unique(project_id, freelancer_id)와 결과 보존 요구 준수 | 구현 |
| 알림 event_key와 수신자의 조합으로 중복 방지 | 네트워크 재시도로 같은 알림이 반복 생성되는 문제 방지 | 구현 |
| JS 알림 함수와 업무 RPC는 같은 SQL 생성 함수를 사용 | 공통 저장 경로를 유지하면서 트랜잭션 보장. RPC 밖에서 추가 알림 생성 안 함 | 구현, 4·5번 전달 필요 |
| 수락 프리랜서 알림은 내 지원 현황으로 연결 | 계약 ID는 4번이 생성하므로 미리 존재하지 않는 계약 주소를 만들지 않음 | 구현 |
| 안 읽은 개수 최초 조회 + Realtime + 30초 보완 조회 | Realtime 미설정·연결 단절에서도 개수를 다시 확인 | 구현, 팀 환경 검증 필요 |
| 알림 30개 페이지 단위 조회 | 오래 쌓인 알림도 유실하지 않고 조회량 제한 | 구현 |
| REA 미연결로 공개 브라우저 조사 대체 | 사용자가 허용한 대안. 설치·실행하지 않은 도구를 사용했다고 기록하지 않음 | 실행 |

새 앱 라이브러리 추가, package.json/lock 변경, 타 담당 폴더 수정, 실 DB 적용, 외부 메시지 발송은 하지 않았다.
