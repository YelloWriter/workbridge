## 1. 목적과 범위

프리랜서가 프로젝트에 지원하고, 의뢰인이 한 명을 선정하면 다른 대기 지원을 자동으로 거절한다. 당사자는 알림과 내 지원 현황에서 결과를 확인한다. 모집 마감도 지원 결과와 알림에 함께 반영한다.

이 문서는 **3번 담당으로 구현한 기능**을 설명한다. 로그인·프로필은 1번, 프로젝트 탐색·등록·마감 호출은 2번, 금액 협의·계약·서명은 4번, 결제·납품·리뷰는 5번 담당이다. 다른 담당 기능은 연결 지점만 명시한다.

## 2. 구현·확인 상태

| 구분 | 상태와 근거 |
| --- | --- |
| 지원 / 지원자 관리 / 내 지원 현황 / 알림 목록 | 화면과 서버 처리 구현. 로컬 세 계정으로 확인 |
| 중복 방지 / 수락·자동 거절 / 마감 / 권한 | SQL `0300`~`0303` 구현. 임시 PostgreSQL에서 검사 |
| 알림 종 / 실시간 갱신 | 구현. 로컬 WebSocket 대역으로 확인. 공통 헤더 삽입은 1번 작업 필요 |
| 프로젝트 상세 연결 | 최신 main에 2번의 지원·지원자 관리 링크와 마감 RPC 호출 코드 반영. 공용 DB에서 이어지는 시연은 남음 |
| 계약 연결 | 협의 시작 금액 저장, 계약 목록 링크 제공. 계약 생성·실제 협의 연동은 4번과 확인 필요 |
| 공용 Supabase | 마지막 직접 확인은 2026-11-24. 공개 키로 프로젝트 조회·시연 계정 로그인 성공. 지원·알림 API는 미노출 오류, 관리 SQL은 권한 거절. 이후 적용 여부는 재확인하지 않음 |
| 실제 서비스 검증 | 공용 DB에서 의뢰인 1명·프리랜서 2명 전체 시연 및 실제 Supabase Realtime 수신 미확인 |

소스 구현과 공용 DB 사용 준비는 별도로 기록한다. 이번 문서 작성에서는 DB를 변경하지 않았다. 이전 작업 기록은 당시 상태이며, 최신 설명은 이 문서의 기준일과 확인 범위를 따른다.

## 3. 사용자와 권한

| 사용자 | 할 수 있는 일 |
| --- | --- |
| 비로그인 방문자 | 지원·내 지원 현황·알림 이용 시 로그인 화면으로 이동 |
| 활동 중인 프리랜서 | 자신의 지원서 제출·조회, 자신의 알림 조회·읽음 처리 |
| 프로젝트를 등록한 활동 중인 의뢰인 | 그 프로젝트의 지원서 조회·수락·거절, 자신의 알림 조회·읽음 처리 |
| 다른 의뢰인·다른 프리랜서 | 남의 비공개 지원서·알림 조회 불가 |
| 탈퇴 처리된 계정 | 지원·알림 이용 차단 |

역할을 선택하지 않은 회원은 역할 선택으로 보낸다. 지원하려면 프로필의 **이름**이 있어야 한다. 프로필의 자기소개·분야·기술은 현재 선택 입력이다. 지원서에 작성하는 자기소개는 별도의 필수 항목이다.

## 4. 기능 목록

| ID | 기능 | 사용자 | 동작과 완료 기준 |
| --- | --- | --- | --- |
| APP-01 | 지원 화면 진입 | 프리랜서 | 모집 중 지원 폼 표시. 미로그인은 로그인, 이름 미입력은 프로필로 이동 |
| APP-02 | 지원서 제출 | 프리랜서 | 자기소개·예상 금액·기간 저장 후 내 지원 현황 이동. 의뢰인 알림 생성 |
| APP-03 | 중복 지원 방지 | 프리랜서 | 같은 프로젝트·같은 회원 한 번만 지원. 거절되어도 재지원 불가 |
| APP-04 | 지원자 목록·지원서 보기 | 프로젝트 의뢰인 | 이름·프로필 링크·금액·기간·상태·지원서 확인. 30개씩 표시 |
| APP-05 | 지원자 수락 | 프로젝트 의뢰인 | 금액 입력 후 한 명 수락. 다른 대기 지원 자동 거절, 프로젝트 계약 대기, 대상별 알림 |
| APP-06 | 직접 거절 | 프로젝트 의뢰인 | 대기 지원 한 건을 직접 거절로 변경하고 해당 프리랜서에게 알림 |
| APP-07 | 모집 마감 처리 | 2번 화면·서버 호출 | 대기 지원 일괄 거절·프로젝트 마감·지원자 전원 알림 |
| APP-08 | 내 지원 현황 | 프리랜서 | 상태·거절 이유·제출 내용·협의 시작 금액을 계속 확인. 30개씩 표시 |
| NTF-01 | 필수 알림 5종 | 의뢰인·프리랜서 | 지원·수락·자동 거절·직접 거절·모집 마감을 대상자에게 저장 |
| NTF-02 | 알림 목록 | 수신 회원 | 최신순 30개씩, 제목·본문·일시·읽음 여부와 전체 미확인 개수 표시 |
| NTF-03 | 알림 선택·이동 | 수신 회원 | 본인 알림 읽음 처리 후 관련 내부 화면 이동 |
| NTF-04 | 모두 읽음 | 수신 회원 | 모든 페이지에 걸친 본인의 미확인 알림 읽음 처리 |
| NTF-05 | 알림 종 | 수신 회원 | 미확인 개수, 100개 이상 `99+`, 개수 미확인·실패 `!`. 누르면 목록 이동 |
| NTF-06 | 자동 갱신 | 수신 회원 | 새 알림·읽음에 따라 개수·목록 갱신. 연결 실패는 주기 조회로 보완 |
| NTF-07 | 공용 서버 알림 함수 | 팀 서버 코드 | `createNotification()` 제공. 업무 변경과 묶는 알림은 업무 DB 함수 안에서 공통 저장 함수 호출 |

## 5. 화면과 사용 흐름

| 주소 | 화면 구성 | 정상 동작 | 예외·빈 상태 |
| --- | --- | --- | --- |
| `/projects/[id]/apply` | 제목, 자기소개, 예상 금액·기간, 제출 | 제출 후 `/me/applications` 이동 | 중복은 현황 링크. 모집 전·마감 안내. 잘못된 ID·없는 프로젝트는 404 |
| `/projects/[id]/applicants` | 건수, 지원자 카드, 지원서 펼치기, 수락·거절 | 처리 후 목록 갱신. 선정 후 계약 안내 | 소유자가 아니면 404. 지원자 없음 안내. 결정된 지원에는 처리 버튼 없음 |
| `/me/applications` | 건수, 프로젝트, 상태·사유, 제안·선정 금액, 기간·일시, 지원서 | 수락이면 계약 목록 링크 | 의뢰인에게 관리 메뉴 안내. 내역 없으면 프로젝트 찾기 링크 |
| `/notifications` | 미확인 개수, 모두 읽음, 항목 강조, 제목·본문·일시, 이전·다음 | 항목 선택 시 읽음 후 이동 | 알림 없음 안내. 읽음 실패는 재시도 안내 |

1. 2번 프로젝트 상세에서 **지원하기**를 누른다.
2. 로그인·역할·활동 상태를 검사한다. 이름이 없으면 `/me/profile?next=<원래 지원 주소>`로 보낸다.
3. 프로필 저장 후 원래 지원 주소로 돌아와 지원서를 제출한다.
4. 지원서는 검토중으로 저장되고 의뢰인에게 알림이 생긴다. 프리랜서는 내 지원 현황으로 이동한다.
5. 의뢰인이 지원자 관리에서 수락하거나 개별 거절한다.
6. 수락하면 다른 대기 지원은 자동 거절되고 각자의 알림·지원 현황에 결과가 남는다.

수락 금액은 **계약 협의를 시작하는 금액**이다. 수락만으로 계약 생성·서명·결제가 완료되지는 않는다.

## 6. 입력과 업무 규칙

| 입력 | 필수 | 허용 범위 |
| --- | --- | --- |
| 지원서 자기소개 `cover_letter` | 예 | 앞뒤 공백 제거 후 1~5,000자 |
| 예상 금액 `proposed_amount` | 예 | 1~999,999,999,999원, 정수 |
| 예상 기간 `proposed_days` | 예 | 1~3,650일, 정수 |
| 수락 금액 `agreed_amount` | 예 | 1~999,999,999,999원, 정수. 기본값은 지원 금액 |
| 자동 거절 확인 체크 | 수락 폼 필수 | 브라우저 제출 전 확인용. 서버 권한 검사는 별도 수행 |

- 제출 시 `recruiting`이고 시작 시각 이상·종료 시각 미만이어야 한다. 시각이 빠져도 제출을 거부한다.
- 지원서 수정·철회·재지원 기능은 없다. 거절 기록도 삭제하지 않는다.
- 프로젝트당 미삭제 선정 지원은 최대 한 건이다.
- 수락은 선정 지원·다른 지원·프로젝트·알림을 한 번에 저장한다. 중간에 실패하면 모두 취소한다.
- 수락·직접 거절은 대기 지원과 recruiting 프로젝트에서 처리한다. 종료 시각만 지났고 아직 마감 처리 전이면 기존 지원의 선정은 가능하다.
- 모집 마감은 기존 직접 거절 이유를 유지하면서 그 지원자에게도 마감 알림을 보낸다.
- 합의 결렬 후 모집 재개는 4번 담당이다. 자동 거절된 지원은 복원하지 않으며 재지원도 허용하지 않는다.

## 7. 상태와 알림

| 지원 저장값 | 화면 표시 / 의미 |
| --- | --- |
| `pending` | 검토중 |
| `accepted` | 수락, 계약 협의 대기 |
| `rejected` + `manual` | 거절 / 의뢰인 직접 거절 |
| `rejected` + `auto` | 거절 / 다른 지원자 선정 |
| `rejected` + `closed` | 거절 / 모집 마감 |
| `rejected` + `negotiation_failed` | 거절 / 금액 합의 결렬. 4번이 변경한 결과 표시 지원 |

수락 시 프로젝트는 `recruiting → contract_pending`, 마감 시 `recruiting → closed`로 바뀐다.

| 알림 type | 받는 사람 | 누른 뒤 이동 |
| --- | --- | --- |
| `application_submitted` | 의뢰인 | `/projects/[id]/applicants` |
| `application_accepted` | 선정 프리랜서 | `/me/applications` |
| `application_accepted` | 의뢰인, 선정 처리 확인 | `/projects/[id]/applicants` |
| `application_auto_rejected` | 다른 대기 지원자 | `/me/applications` |
| `application_rejected` | 직접 거절된 프리랜서 | `/me/applications` |
| `project_closed` | 해당 프로젝트 지원자 전원 | `/me/applications` |

알림은 서비스 내부 목록·종으로 제공한다. 이메일·문자·카카오·브라우저 푸시 발송은 없다. 계약·결제 알림 종류도 저장할 수 있지만 사건 발생 처리는 4·5번에서 연결한다.

## 8. 팀 연결과 검증

| 담당 | 코드 기준 연결 상태 | 남은 확인 |
| --- | --- | --- |
| 1번 | 프로필 이름 필수·next 복귀 로컬 확인. `NotificationBellWidget` 제공 | 헤더 삽입, 공용 SQL·환경 준비 |
| 2번 | 최신 main에서 지원·관리 링크와 마감 RPC 호출 확인 | 공용 DB에서 지원·마감 및 프로젝트 표시 통합 확인 |
| 4번 | 지원 ID·`accepted_agreed_amount`·`accepted_at` 제공 | 계약 생성·중복 방지·합의 결렬 처리 연결 |
| 4·5번 | JS `createNotification`, SQL `create_notification` 제공 | 업무 권한 검사와 트랜잭션 내부 알림 연결 |

현재 2번의 시간 만료 마감은 화면 조회 후 실행하는 방식이며 서버 비밀 키가 필요하다. 아무도 접속하지 않으면 실행되지 않는다. 상시 예약 작업까지 완료한 것으로 보지 않는다.

2026-11-24 기록상 임시 DB 72개, 구독 수명 38개, 로컬 서비스 흐름 22개 검사가 통과했다. 로컬 화면에서 세 계정의 지원·수락·자동 거절·각자 알림·읽음·프로필 복귀·자동 갱신을 확인했다. 실제 공용 Supabase 통합 성공을 의미하지 않는다. [세부 검증 기준과 기록](./3-applications-notifications-detail.md#10-검증-명세와-기록)을 참고한다.

입력 범위·금액 인계·원자적 처리·프로필 조건 등의 이유는 [초기 결정](../decisions/2026-11-23-3-applications-notifications.md), [접근 보완](../decisions/2026-11-24-3-applications-notifications.md), [실시간·프로필 결정](../decisions/2026-11-24-3-realtime.md)에 기록되어 있다. 이번 명세는 기존 구현을 설명하며 새 상태값·DB 구조·기능 요구를 추가하지 않는다.
