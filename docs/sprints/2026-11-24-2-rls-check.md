## 빈틈 1개: 의뢰인이 본인 프로젝트의 상태를 직접 바꿀 수 있습니다

- **확인한 것:** 의뢰인 계정으로 본인 프로젝트의 `status` 를 `completed`(완료)로 직접 바꾸는 요청이 **막히지 않고 바뀌었습니다.** (시험 프로젝트에서만 했고 바로 되돌려 지웠습니다.)
- **이유:** 0200 의 수정 규칙이 "의뢰인 본인만 수정"이라 상태 칸도 같이 열려 있습니다. 수락(3번), 합의·서명(4번), 결제·납품·완료(5번)는 각자의 DB 함수로 상태를 바꾸는데, 화면을 거치지 않고 DB에 직접 요청하면 의뢰인이 그 함수들을 건너뛸 수 있습니다.
- **영향:** 결제 없이 "작업 중"이나 "완료"로 바꾸거나, 진행 중인 계약의 프로젝트를 되돌릴 수 있습니다. 화면에는 그런 버튼이 없지만 DB 요청은 가능합니다.
- **결정(2026-11-24, 사용자):** `0203_project_status_guard.sql` 로 막습니다. 직접 보내는 요청으로는 `scheduled` ↔ `recruiting` 만 바꿀 수 있고(지원자가 있으면 `scheduled` 로 되돌릴 수 없음), 나머지 상태 변경은 각 담당의 DB 함수로만 가능합니다. 서버 전용 서비스 키와 대시보드 SQL Editor 는 막지 않습니다.
- **다른 번호 함수가 영향받지 않는지 확인:** 3번(`0301`)·5번(`0500`, `0501`)의 실제 SQL 을 임시 DB 에 올려 돌렸습니다. 3번 수락(→계약 대기)·모집 마감(→모집 마감), 5번 결제 확인(→작업 중)·납품 요청(→납품 요청)·완료 승인(→완료)이 모두 그대로 동작했고, 의뢰인이 직접 보내는 같은 변경은 모두 거부되었습니다. 31개 모두 통과.
- **원리:** 함수 안에서 하는 변경은 함수 주인 권한으로 실행되므로 막히지 않습니다. 이 함수들이 모두 `security definer` 이기 때문에 가능합니다.
- **4번에게 알릴 것:** 4번 브랜치에는 아직 SQL 이 없어서 확인하지 못했습니다. 합의 결렬(계약 대기 → 모집 중 복귀)과 서명 함수는 **반드시 `security definer` 로** 만들어야 합니다. 그렇지 않으면 `STATUS_CHANGE_NOT_ALLOWED` 로 막힙니다. (임시 DB 에서 두 경우 모두 확인)
- **팀 DB 적용(2026-11-24 완료):** 사용자가 SQL Editor 에서 `0203` 을 실행했고("Success. No rows returned"), 같은 시연 계정 2개로 다시 확인했습니다. 시험 프로젝트를 만들어 쓰고 지웠으며 시연 프로젝트는 그대로입니다. 13개 모두 기대대로입니다.
  - 의뢰인이 직접 `in_progress`, `completed`, `closed`, `contract_pending`, `delivered`, `cancelled` 로 바꾸는 요청 6개: **모두 403, `STATUS_CHANGE_NOT_ALLOWED` 로 막힘.** 상태는 그대로 `recruiting`.
  - 제목·예산 수정: 가능. 지원자가 없을 때 `recruiting` ↔ `scheduled`: 가능.
  - 프리랜서·비로그인이 남의 프로젝트 상태를 바꾸는 요청: 바뀐 줄 0개.
- **위의 "빈틈"은 닫혔습니다.** 아직 확인하지 못한 것: 지원자가 있을 때 `scheduled` 로 되돌리기 거부(지원 테이블이 팀 DB에 없음, 임시 DB 에서는 확인), 4번 함수와의 동작.
- 취소(`cancelled`)로 바꾸는 기능은 아직 어느 번호에도 없고, 만들 때는 같은 방식의 DB 함수가 필요합니다.
