최종 `npm run build` 통과. 검증용 임시 페이지를 제거한 뒤 기본 환경으로 다시 빌드했다. 3번 담당 파일의 ESLint 검사는 통과했다. 전체 ESLint는 main에서 들어온 1번 Header의 기존 오류 1건으로 실패하며 아래 인계 사항에 위치와 수정 방향을 남겼다. 브라우저 검증 서버 로그에는 런타임 오류가 없었다.

사용자의 요청은 모든 작업을 끝낸 뒤 마지막에 push하는 것이다. 실제 Supabase 검증을 끝내지 못한 상태이므로 최종 push는 보류한다. 정상 연결이 확인되면 실환경 스크립트와 세 계정 시연을 수행하고 그 결과를 추가한 뒤 3번 브랜치만 push한다.

이번 기록은 11월 23일·24일 초기 기록을 대체하는 최신 범위다. 이전 기록은 당시 상황으로 유지한다.

## 로컬 시연 재현

저장소 package.json/lock에 새 라이브러리를 추가하지 않았다. PGlite와 선택적인 ws는 별도 작업 폴더에 설치해 사용했다.

1. `WORKBRIDGE_PGLITE_MODULE`에 PGlite `dist/index.js`, `WORKBRIDGE_WS_MODULE`에 ws의 `wrapper.mjs` 절대 경로를 지정한다.
2. 저장소 루트에서 `node src/components/applications/tests/browser-fixture.mjs` 실행. API와 WebSocket 대역은 127.0.0.1:3014에만 열린다.
3. `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:3014 NEXT_PUBLIC_SUPABASE_ANON_KEY=local-fixture-anon npm run build` 실행.
4. 같은 환경 변수로 `npm run start -- --hostname 127.0.0.1 --port 3003` 실행.
5. `http://127.0.0.1:3014/test`에서 세 계정을 바꿔 가며 지원·선정·알림을 확인한다. 다시 시작하면 임시 DB는 초기화된다.
6. 자동 서비스 검증은 아래 스크립트에 `local-1@test.example`, `local-2@test.example`, `local-3@test.example` 계정을 지정한다. 로컬 비밀번호는 코드에 표시된 검증 전용 값이며 실제 계정과 무관하다.

## 공용 Supabase 검증 실행

필요한 것: 정상 URL·공개 anon/publishable 키, 적용 완료된 0100/0200/0201/0300/0301/0302/0303, **서로 다른 의뢰인 1/프리랜서 2 계정**과 프로필 이름. service_role 키는 이 시연 스크립트에는 필요하지 않다. SQL 적용은 권한이 있는 팀 담당자가 해야 한다.

계정 JSON 파일은 저장소 밖에 만들고 Git에 올리지 않는다. 모양은 다음과 같으며 실제 값은 여기에 쓰지 않는다.

```json
{
  "client": { "email": "<의뢰인 이메일>", "password": "<비밀번호>" },
  "freelancerA": { "email": "<첫 프리랜서 이메일>", "password": "<비밀번호>" },
  "freelancerB": { "email": "<둘째 프리랜서 이메일>", "password": "<비밀번호>" }
}
```

`WORKBRIDGE_TEST_ACCOUNTS`에 그 파일 경로, `WORKBRIDGE_REPORT_PATH`에 결과 JSON 파일 경로를 지정한다.

```bash
node --env-file=.env.local src/components/applications/tests/live-smoke.mjs
node --env-file=.env.local src/components/applications/tests/live-smoke.mjs --run
```

첫 명령은 준비 확인만 한다. 두 번째는 `[3번 시연]` 제목의 프로젝트 3개와 지원·결정·알림 데이터를 남긴다. 삭제하지 않으므로 시연 자료로 재사용할 수 있다. 계정/DB 연결 실패는 실제 검증 실패로 기록하고 성공으로 표시하지 않는다.

## 팀 통합 전달

- **1번:** Header의 `data-slot="header-notifications"` 자리에 NotificationBellWidget을 넣는다. 전체 ESLint 검사에서 기존 `src/components/layout/header.tsx:16`의 `react-hooks/set-state-in-effect` 오류가 확인됐다. 초기 상태가 이미 out이므로 환경 변수 누락 분기의 동기 setSession을 제거하는 수정이 가능하다. 3번은 담당 범위 때문에 수정하지 않았다. Vercel/Supabase 공개 연결 값도 확인 필요.
- **2번:** 수동/자동 모집 마감은 상태를 먼저 변경하지 않고 `close_project_applications`를 호출한다. 실제 프로젝트 화면의 지원·지원자 관리 링크를 연결한다.
- **4번:** accepted 지원의 application_id·accepted_agreed_amount를 계약 생성에 사용한다. 합의 결렬의 프로젝트/지원/알림 변경은 하나의 RPC에서 처리한다.
- **4·5번:** 단독 서버 알림은 createNotification, 업무 변경과 묶는 알림은 업무 RPC 내부의 create_notification을 사용한다.

메시지를 대신 보내거나 다른 담당자의 폴더·배포 설정을 수정하지 않았다.

## 짧은 회고

실제 팀 SQL을 조기에 합쳐 nullable 역할과 프로필 필수 조건 차이를 발견할 수 있었다. 실시간 목록을 헤더와 분리하면서 각자 동시에 개발할 때의 의존성도 줄였다. 단위 검사만으로는 로컬 CORS 대역의 누락을 찾기 어려웠고, 브라우저와 WebSocket 연결을 같이 확인한 뒤 보완했다.

앞으로는 공용 DB SQL 적용 여부·정상 키·컴포넌트의 서버/클라이언트 사용 방식을 팀 인터페이스와 함께 먼저 확인해야 한다. 로컬 성공, 실제 Supabase 성공, 전체 배포 성공을 각각 기록하는 방식은 유지한다.
